I'm Omar, an AI engineer who likes owning a system from start to finish: ingestion and retrieval design, evaluation and escalation logic, and the deployment and monitoring that keep it working once real users arrive.

I got into AI through generative vision. For my graduation project I fine-tuned Stable Diffusion to generate floor plans, and that work became a peer-reviewed paper. Since then I've focused on language: RAG, agents built with LangGraph, and systems that work in both Arabic and English.

LLM · RAG · Human-in-the-loop

Handbook Assistant

A customer support agent that knows when to ask a human.

A support agent for a computer science institute. It answers student questions from the CS and IS handbooks, and when it can't answer confidently it opens a ticket for a human advisor instead of guessing. When the advisor replies, the answer goes back into the student's conversation, and the advisor can add it to the knowledge base so the same question is answered automatically next time.

View the code on GitHub

The problem

Students ask about registration, GPA rules and graduation requirements, and the answers are in two long handbooks, partly in Arabic. A normal RAG chatbot answers every question with the same confidence, even when retrieval found nothing useful. On academic rules, a confident wrong answer does more harm than "let me ask an advisor."

What I built

An agent that answers only when three separate checks agree it should, backed by a ticket system that survives restarts, a learning loop where the advisor decides what gets added, and the monitoring to run it all in production.

Six decisions I'd defend in a design review

  1. Separate judges, not a confidence score

    Models are poorly calibrated when asked to rate their own confidence. Instead, three single-purpose judges each check something different against different evidence. The answer-relevance judge is deliberately not shown the excerpts, so it can catch an answer that is well grounded but answers the wrong question.

  2. Judges fail closed

    If a judge returns output it can't parse, or can't be reached, the question escalates. A judge that failed open would let answers through exactly when the checking system is broken.

  3. Escalation ends the run

    Nothing stays paused in memory waiting for a human who might take days. An open ticket is just a database row, so it survives restarts and scales. The student sees the advisor's reply on their next visit.

  4. The advisor decides what the agent learns

    Resolving a ticket and adding its answer to the knowledge base are separate steps. One judge suggests whether the answer is general enough to reuse, and another holds back any answer that contradicts the handbook. Handbook text always ranks first.

  5. One source of truth

    Postgres holds tickets, chunks and conversation history. The pgvector index is rebuilt from it and can be dropped and pushed again without losing anything. Syncing deletes and re-inserts by a stable key, so it never creates duplicates.

  6. Thin nodes, logic in controllers

    Each LangGraph node calls one controller method. The advisor's HTTP endpoint calls the same controller as the graph, and all 115 tests run without a database, API keys or the graph.

"If the model provider goes down, every question escalates, while /chat still returns 200 with normal latency. A standard dashboard would look perfectly healthy."

That's the failure I designed the monitoring around.

So I added metrics specific to this system. judge_failures_total{gate} is the only signal that separates "the provider is down" from "retrieval is bad," two problems that need opposite fixes.

  • ObservabilityPrometheus and Grafana, 7 alert rules checked with promtool, metrics labelled by route template so the number of series stays bounded, and JSON logs with a correlation ID for each conversation
  • InfrastructureDocker Compose with one command (make up), nginx as the only public port, Alembic migrations on startup, and memory limits on every service
  • CorrectnessA ticket state machine with an audit trail, optimistic locking that returns a 409 on conflict, and idempotent syncing to the vector index
  • Testing115 tests in GitHub Actions, plus Locust load profiles

Mizan ميزان

mīzān, noun: a balance; a pair of scales.

An agentic RAG assistant that answers questions about Egyptian labor law in Arabic and English. It is built as a stateful LangGraph graph: it grades what it retrieves, and when the results are weak it rewrites the question into more precise legal wording and searches again. Trustcall remembers each user across sessions, and Groq-hosted Llama 3.3 70B keeps answers fast.
