01 · Featured case study

Handbook Assistant: a customer support agent that knows when to ask a human

Runs end to end View on GitHub →

The problem

Students ask about registration, GPA rules and graduation requirements, and the answers are in two long department handbooks (CS and IS), partly in Arabic. A normal RAG chatbot answers every question with the same confidence, even when retrieval found nothing useful. On academic rules, a confident wrong answer does more harm than "let me ask an advisor."

What I built

An agent that answers only when three separate checks agree it should. Otherwise it opens a ticket for a human advisor. The advisor's reply goes back into the student's conversation, and the advisor can choose to add it to the knowledge base so the same question is answered automatically next time. The whole thing ships as a monitored, tested service.

Key design decisions

01

Separate judges, not a confidence score

Models are poorly calibrated when asked to "rate your confidence from 0 to 1." Instead, three single-purpose judges each check something different against different evidence. The answer-relevance judge is deliberately not shown the excerpts, so it can catch an answer that is well grounded but answers the wrong question.

02

Judges fail closed

If a judge returns output it can't parse, or can't be reached, the question escalates. A judge that failed open would let answers through exactly when the checking system is broken.

03

Escalation ends the run

Nothing stays paused in memory waiting for a human who might take days. An open ticket is just a database row, so it survives restarts and scales. The advisor's reply is written back into the saved conversation, and the student sees it on their next visit.

04

The advisor decides what the agent learns

Resolving a ticket and adding its answer to the knowledge base are two separate steps. One judge suggests whether the answer is general enough to reuse, and another holds back any answer that contradicts the handbook. Handbook text always ranks above advisor answers at retrieval.

05

One source of truth

Postgres holds tickets, chunks and conversation history. The pgvector index is rebuilt from it and can be dropped and pushed again without losing anything. Every sync deletes and re-inserts by a stable key, so running it twice never creates duplicates.

06

Thin graph nodes, logic in controllers

Each LangGraph node reads the state, calls one controller method and writes the result back. The advisor's HTTP endpoint calls the same controller as the graph, and all 115 tests run without a database, API keys or the graph.

Built to run in production

The most dangerous failure in this system doesn't show up in HTTP metrics. If the model provider slows down or fails, the judges fail closed and every question escalates, while /chat still returns 200 with normal latency. A dashboard of requests and errors would look perfectly healthy.

So I added metrics specific to this system. judge_failures_total{gate} is the only signal that separates "the provider is down" from "retrieval is bad," two problems that need opposite fixes.

  • ObservabilityPrometheus and Grafana, 7 alert rules checked with promtool, metrics labelled by route template so the number of series stays bounded, and structlog JSON logs with a correlation ID for each conversation
  • InfrastructureDocker Compose with one command (make up), nginx as the only public port, Alembic migrations that run on startup, and memory limits on every service
  • CorrectnessA ticket state machine with an audit trail, optimistic locking that returns a 409 on conflict, and idempotent syncing to the vector index
  • Testing115 tests in GitHub Actions, plus Locust load profiles
